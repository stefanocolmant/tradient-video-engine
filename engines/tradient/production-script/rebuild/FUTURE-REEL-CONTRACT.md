# Author new scenes by meaning, then prove them in motion

A23 remains Stephane's positive quality reference. The rejected Rules before reactions v2 is NOT a visual benchmark. Its technical validation and detailed-looking document did not establish visual quality.

## The order of work
1. Write the informative narration, then choose/freeze the continuous performance and word timing.
2. For each spoken action, identify the real object, input state, visible cause, visible result and exact word anchor. If the scene needs its label to explain why a decorative machine moves, redesign it.
3. Carry explicit identities across cuts. A quantity, order, report or chart must have one authoritative state. Distinguish configuration, condition, submission, acceptance, execution and report.
4. Design camera movement to reveal information: enter a real surface, follow a meaningful object, change scale, reveal the next cause. No prolonged camera drift in place of progression.
5. Author component geometry, material response, lighting, composition and choreography. The template does not invent new geometry. Existing components are building materials, not a finished film.
6. Record all timed events in the score. Animation, sound placement and readable second-by-second documentation must resolve the same frame records. Fail on missing required events; no hidden fallback times.
7. Make the opening, central transformation and resolution as moving proofs first. Inspect at720×1280 and360×640 against relevant A23 passages. Compare projected scale, depth layers, physical detail, coordinated action, material response, readable meaning and camera progression.
8. Correct failures in source and in the production recipe. Preserve rejected attempts and exact change notes. Only then render the full film.
9. Check every shot/cut, word-action linkage, direct/backward seeking, state continuity, quantities, audio alignment, complete decode and the actual delivered file. Technical success and user aesthetic acceptance remain separate.

## Required production fields
- Film: dimensions, fps, frame count, frozen audio hashes, fonts/assets, renderer/capture environment.
- Shared data: named entities, OHLC/value data, state machine and numeric invariants.
- Event: ID, unique phrase/occurrence, anchorFrame, firstFrame/endFrame, before/after, visible action, sound, actual renderer consumer.
- Shot: inclusive start/exclusive end, scene adapter, exact camera eye/target/FOV knots, continuity, active action and caption placement.
- Recipe: dimensions, hierarchy, geometry method, materials, texture/shader construction, light/shadows, camera scale, motion formulas and constraints, source files, consumed versus documentation-only fields, known failures.
- Every second, including partial tail: narration, visible captions, actual event progress, active scene layers, evaluated camera endpoints, retained and changed state, supporting motion, light/material response, sound and incoming/outgoing continuity.

## Specific lessons from this rebuild
- Do not use a conveyor, dial, press or printer as an unexplained stand-in for a trading concept.
- Reusing A23's optical lens requires ray-mapping the SAME selected card texture; test legibility through the lens.
- A candle height must be scaled from its own original geometry height. A universal minimum body size can amplify a small price move.
- Match a unique multiword narration phrase. “updates” alone matched the wrong occurrence; “updates the system” identifies report receipt.
- Execution records must form before the return journey begins. Requested quantity equals filled plus remaining at every frame.
- Cursor contact and action labels must be readable at the spoken cue, not only later in a scene.
- Move both the camera and information through connected scenes; do not turn a scene into an unchanged phone or panel hold.
- A correct quantity diagram can still need more visual refinement. Do not mark a new library component aesthetically approved until Stephane selects it.

## Completion-audit lessons
- A procedural screen's cache key must serialize all painter inputs. Omitting one state made definition highlighting depend on which frames had already rendered. Keep the screen-state function pure and test both state/key changes and rendered direct/backward seeks.
- When fields form a document, assign different landing coordinates and reveal the destination text after arrival. Three labels moving to one center is overlap, not assembly.
- In an attention comparison, show the same condition and actual instruction origin; move the camera between those causes. Two unchanged charts plus tiny markers do not communicate enough progression.
- A test/replay view must reveal its inputs and outputs in sequence. Showing all outcomes immediately is a static table, not a replay.
- The report display must consume the shared reported state. Do not switch the numbers at an unrelated travel-opacity threshold.
- Validate event ranges, camera knots, supported values and lifecycle ordering in the renderer itself. A separate preflight command cannot guard every future entry point.
- Test the extracted archive with a fresh dependency install and a full render. Syntax checks and a source zip do not establish portability.
